# Configuration schema — v1alpha1

Formal schema for the Songbird configuration (RA constraint **C-005**, requirements **R-020.2 / R-020.3 / R-052**).

```
schema/                     (this directory)
  songbird.schema.json      entry point: dispatches on `kind`
  common.schema.json        shared $defs (names, CIDR, ports, metadata, ...)
  system.schema.json        kind: System         (singleton, global settings — FortiGate "config system *")
  color.schema.json         kind: Color          (palette; meaning lives in metadata.comment)
  interface.schema.json     kind: Interface      (new)
  zone.schema.json          kind: Zone           (new, R-046)
  address.schema.json       kind: Address
  addressgroup.schema.json  kind: AddressGroup
  service.schema.json       kind: Service
  servicegroup.schema.json  kind: ServiceGroup
  ruleset.schema.json       kind: RuleSet        (replaces v0 `Rules`; NAT is a section of the rule)
examples/
  valid/                    a complete small-office configuration (46 objects: system, predefined any/any6, palette, 5 interfaces, 3 zones, 6 rule sets)
  invalid/                  43 files, each violating exactly one rule
validate.py                 prototype of `songbird validate <dir>` (schema + semantic checks)
```

## Why JSON Schema (and not CUE)

| | JSON Schema 2020-12 | CUE |
|---|---|---|
| Editor support (VS Code autocomplete, inline errors) | Yes, via `yaml-language-server` with one comment line | No mainstream YAML editor integration |
| Go validation library | `santhosh-tekuri/jsonschema` (mature, 2020-12) | `cuelang.org/go` (heavier, API less stable) |
| Can express cross-object references ("destination must be an existing Address") | **No** | Yes, but only when all files are loaded as one CUE package |
| Generates Go structs | Yes (`omissis/go-jsonschema`) | Yes (`cue exp gengotypes`, experimental) |
| Who already knows it | Everyone who wrote a Kubernetes CRD | Few |

Decision: **JSON Schema is the normative artifact**; the cross-object rules that it cannot express are an explicit, enumerated list implemented in the validator (see below). This is the same split Kubernetes uses (OpenAPI schema in the CRD + admission webhook for semantics). If the semantic rule list grows beyond ~30 rules, revisit CUE.

## Design decisions (each is a candidate ADR)

1. **`metadata.name` is the primary key.** `uuid` is optional, generated by the system, and exists only so the UI can follow renames. Names are DNS-label-like (`^[a-z0-9]([a-z0-9._-]*[a-z0-9])?$`), max 63 chars; only `none` is reserved. **`any` is not a keyword**: `any` / `any6` are predefined Addresses (`0.0.0.0/0`, `::/0`) and `any` is also the predefined Service (every protocol and port) — ordinary references that live in their own namespaces (RA R-012.1, R-010.1). They ship with the product: the validator injects them when a tree does not contain them and rejects any modification (`predefined-immutable`).
2. **Three shared namespaces**, so that a Policy field can hold a plain string without a `kind:` qualifier (FortiGate behaviour):
   - *address* namespace: `Address`, `AddressGroup`
   - *service* namespace: `Service`, `ServiceGroup`
   - *network* namespace: `Interface`, `Zone`
   - *color* namespace: `Color`
3. **`kind: Color` is a first-class palette entry, not decoration.** A Color has a `hex`; what it stands for ("green = Backup/Veeam", "blue = main LAN", "red = DMZ") goes in `metadata.comment` like for every other object, so colour acts as a *classification* of similar objects and the UI can show a legend. `metadata.color` on **every** kind (Interface, Zone, Address, AddressGroup, Service, ServiceGroup, RuleSet) is a **reference to a Color name**, never a literal hex (validator: `dangling-ref`). Songbird ships a predefined palette (7 colours, `predefined: true`) whose `hex` is immutable so palettes stay recognisable across installations; users annotate their comment and add their own Colors freely. Two Colors cannot share a hex (`duplicate-hex`).
4. **CIDR only** for subnets (`192.168.0.0/24`), no netmask notation (R-012). Ranges are `{start, end}` of the same family.
5. **Rules live in `RuleSet`, one per `(from, to)` pair** of Interfaces/Zones (kind names are singular, as in Kubernetes: the object is one *set* of rules). The pair is a *match criterion*, so sets for different pairs can never overlap: ordering is the array position, and it only matters inside one file. This resolves the `TODO` in the v0 README with no UUID manifest and no numeric priorities. Consequence: **`any` is forbidden for `from`/`to`** (RA open issue 4) — use a Zone that contains the relevant Interfaces.
6. **NAT is one `nat:` section of the rule, and reuses Address/Service objects — no VirtualIP/NAT kinds.** `nat.type: snat` with optional `translateIpTo` (an Address acting as IP pool; omitted = outgoing interface address, i.e. masquerade, which also covers dynamic WAN addresses). `nat.type: dnat` with required `translateIpTo` (single-host Address or range) and optional `translateServiceTo` (a Service with one tcp/udp/sctp entry and a single port; omitted = port unchanged). **Architectural consequence:** a dnat rule matches destination and service *before* translation (the public address), nftables `prerouting dnat` semantics — not the post-DNAT evaluation of FortiGate VIPs that `dataplane.md` §7 currently assumes. `dataplane.md` must be updated accordingly (the classifier runs on the original tuple; the DNAT lookup follows).
7. **`Zone` membership is declared only in the Zone** (`spec.interfaces`), never on the Interface, so there is exactly one place to look and the "at most one Zone per Interface" rule is checkable.
8. **`Interface.metadata.name` is the user-facing name** (`wan`, `lan1`); the Linux device name is `spec.device`. VLANs reference their parent by object name, not by device.
9. **`additionalProperties: false` everywhere.** A typo (`colour`) is an error, not a silently ignored field.
10. **Every rule has a `name`**, unique within its RuleSet. It is what the Traffic Log (R-026) and the UI show; it also gives Git diffs a stable anchor when rules are reordered.
11. **Interfaces have no `role`.** The former `role` field (and its dangerous default `internal`) is gone: what an Interface may do follows from its Zone, its `allowAccess` and the System Services listening on it. The setup-time UI restriction relies on `allowAccess` only (RA R-031.1); the DHCP server may run on any Interface (R-017.5).
12. **`allowAccess` is a closed list of Management Services** — `https`, `ping`, `ssh` — exactly like FortiGate `allowaccess`. Network services the firewall offers to its hosts (DNS, NTP; DHCP pending RA open issue 13) are **System Services** under `System.spec.systemServices.<service>.listenOn` (Interfaces or Zones); the firewall admits their traffic without a Policy (R-058). This removes the double-definition that `dns` in `allowAccess` + `serveToInterfaces` allowed.
13. **`System` is a singleton** (`metadata.name: "system"`) holding the global settings, structured after FortiGate's `config system global / admin / ntp / dns / session-ttl` and `config log`: `admin` (HTTPS port, session timeout, lockout, trusted hosts, ACME certificate, UI theme), `ntp`, `dns` (forwarder/recursive, upstreams + failover, local records, DNS64), `logging` (rotation, GDPR masking, syslog), `session` (conntrack timeouts, fragments, behaviour on rule change), `nat64`, `git` (GitOps remote and auth), `updates` (A/B channel + window), `threatFeeds`. Every section has defaults; the minimal object is `{hostname}`. Per-interface management access is `Interface.spec.allowAccess` (FortiGate `allowaccess`). **Secrets never appear in clear**: they must use the `ENC[...]` envelope, enforced by the schema (R-020.5).
14. **Serialisation style: every string value is double-quoted** (`kind: "Address"`, `port: 443` stays a number), keys unquoted, 2-space indent, block style with inline `{}`/`[]` only for short leaf maps/lists. This is the canonical form `songbird export` writes and the UI commits, so diffs are stable and types are unambiguous (`"yes"`, `"010"`, `"1e3"` are strings). JSON Schema does not and cannot enforce quoting — a formatter/linter step does.

## Semantic rules (implemented in `validate.py`, not expressible in JSON Schema)

| Rule id | Check |
|---|---|
| `unique-name` | Names unique within each shared namespace (Color has its own namespace) |
| `duplicate-hex` | Two Colors cannot share the same hex |
| `predefined-hex` / `predefined-unknown` / `predefined-shadow` | Predefined palette entries keep their hex; the names of the shipped palette cannot be reused for user colours |
| `dangling-ref` | Every reference resolves to an existing object |
| `wrong-kind` | Reference resolves to an object of an allowed kind for that field |
| `vlan-parent` | VLAN parent is a physical Interface |
| `duplicate-vlan` / `duplicate-device` | `(parent, vlanId)` and `device` unique |
| `pd-source` | `delegatedPrefixFrom` points to a `dhcpv6-pd` Interface |
| `zone-overlap` | An Interface belongs to at most one Zone |
| `range-order` / `range-family` / `cidr` | Address ranges and subnets are well-formed |
| `wrong-kind` on groups | Groups are **flat**: an AddressGroup contains only Addresses, a ServiceGroup only Services (team decision 2026-10-19) |
| `same-interface` | `from != to` for Interfaces |
| `duplicate-pair` | Exactly one RuleSet per `(from, to)` |
| `duplicate-rule` | Rule names unique within a RuleSet |
| `mac-as-destination` | MAC Addresses only as source |
| `nat-address-kind` / `dnat-single-host` | `translateIpTo` is a subnet/range Address; for dnat a single host or range |
| `dnat-any-destination` / `dnat-any-service` | dnat needs an explicit destination; port translation needs an explicit service |
| `dnat-service-shape` / `dnat-protocol-mismatch` | `translateServiceTo` has one tcp/udp/sctp entry with a single port, same protocol as the rule's service |
| `system-singleton` | At most one System object |
| `predefined-immutable` / `predefined-unknown` / `any-protocol` | Shipped `any`/`any6`/Service `any` are immutable; `predefined: true` and `protocol: any` are allowed only on them |
| `unsupported-address-kind` | An enabled rule may not reference an FQDN or MAC Address until the Data Plane supports them (RA R-012.4) |
| `dns64-without-nat64` / `recursive-upstreams` | System cross-section consistency |

## Usage

```bash
# one-off, with uv
uv venv .venv && uv pip install --python .venv/bin/python jsonschema pyyaml
.venv/bin/python validate.py examples/valid        # → 46 objects, 0 errors (exit 0)
.venv/bin/python validate.py examples/invalid      # → 43+ errors (exit 1)

# editor autocomplete: first line of any YAML file
# yaml-language-server: $schema=../../schema/songbird.schema.json
```

`validate.py` is a throwaway prototype whose purpose is to pin down the rule list. The real `songbird validate` is a Go CLI (RA R-052) using `santhosh-tekuri/jsonschema` for layer 1 and a port of the table above for layer 2; the `examples/` tree becomes its test corpus (RA R-020.2 verification).

## Not covered yet (next schema iteration)

`StaticRoute`, `DhcpServer` (pools, reservations, PD), `User`, `Role`, `Notification` (SMTP/webhook/Telegram), `Schedule`. These map to RA §6.3, §6.4, §6.7, §6.8. DNS, logging, GitOps, updates and threat feeds already live in `System`; if any of them grows (e.g. many DHCP pools) it should become its own kind.

## Open questions for the team

1. ~~Should `Address.spec.fqdn` and `.mac` stay in `Address`?~~ **Decided 2026-10-19**: they stay in `Address` (RA R-012.2/.3); enabled rules referencing them are rejected until the Data Plane supports them (R-012.4, rule `unsupported-address-kind`).
2. `RuleSet.spec.rules` may be empty (explicit "nothing allowed between these two"). Keep, or require `minItems: 1` and rely on Default Deny?
3. Multi-document YAML files vs one object per file. The schema is agnostic; Git diffs are cleaner with one-per-file, the UI export is simpler with one-per-kind. Pick one and make `songbird export` enforce it.
4. ~~Can a rule have both snat and dnat (hairpin)?~~ **Decided**: no — RA W-007 excludes hairpin NAT; `nat.type` stays one of the two.
7. **DHCP server** (RA open issue 13): per Interface or `systemServices.dhcp` with one block per Interface? Whichever is chosen, add the coherence rule: a pool advertising the firewall as DNS/NTP requires that Interface (or its Zone) in the corresponding `listenOn`.
5. The predefined palette is hard-coded in the validator (`PREDEFINED_PALETTE`). In the Go implementation it should ship as an embedded YAML (`palette.yaml`) so that the UI, the validator and `songbird export` use the same list. Should the palette be 7, 12 or 16 colours?
6. Service `sourcePort`: kept for completeness, but FortiGate hides it by default. Keep or drop for v1alpha1?
